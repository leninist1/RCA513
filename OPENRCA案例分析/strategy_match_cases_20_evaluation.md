# 20 个 OpenRCA 案例上的策略评价

本文基于 [strategy_pool.md](/mnt/d/projects/openrca/mydocs/strategy_pool.md) 中定义的 `S1` 到 `S5` 五类策略，以及 [strategy_match_cases_20_annotated.md](/mnt/d/projects/openrca/mydocs/strategy_match_cases_20_annotated.md) 中 20 个 OpenRCA 案例的人工标注结果，对每个策略做汇总评价。评价重点不是单个案例是否“能用”，而是该策略是否真的适合它声称适用的那类案例。

## 整体结论

整体上，这个策略池的分工是成立的：

- `S1` 负责入口筛选与候选压缩；
- `S2` 负责资源类候选的强反事实验证；
- `S3` 负责沿传播链回溯、区分源头与受害者；
- `S4` 负责多层部署场景中的层级消歧；
- `S5` 负责用日志、JDBC、状态位等语义硬锚点做最终确认。

从这 20 个案例看，五类策略的角色区分比较清楚，不存在大面积相互替代的情况；更准确地说，它们更像是不同分析阶段的专用工具，而不是一组彼此竞争的统一分类器。

## 各策略评价

### S1 广撒网浅验证

`S1` 是整体最稳的通用入口策略。它在 20 个案例上的平均分最高，为 `1.95`，并且没有任何 `0` 分案例，说明它几乎不会明显误用；同时它获得了 5 次首选和 7 次次选，覆盖面最广。

从标注结果看，`S1` 特别适合网络类问题。对于 `Bank` 的 network latency / packet loss、`Telecom` 的 network delay / loss，以及 `Market` 的初筛场景，`S1` 都能先通过浅层排他性检查快速压缩候选集合，再决定是否进入 `S3` 做传播回溯，或进入 `S4` 做层级消歧。

因此，对 `S1` 的评价是：它的优势在于“低风险、广覆盖、适合作为默认入口”，而不是直接给出最终根因。换言之，`S1` 更像一个稳定的第一步，而不是终判策略。

### S2 单候选深挖验证

`S2` 是资源类案例的主力策略，特点是精度高，但适用面较窄。它在 20 个案例上的平均分为 `1.45`，共有 6 次首选；虽然整体均值不如 `S1`，但这是因为它在不少非资源类案例上直接被标为 `0` 分。

如果只看资源类场景，`S2` 的适配性非常强。`Bank` 的 high CPU usage、high memory usage、high disk I/O、high disk space usage、high JVM CPU load，以及 `Telecom` 的 CPU fault，基本都支持“候选聚焦后做局部异常最强、时间最早、替代解释最弱”的验证思路。

不过，`S2` 的前提条件也比较明确：候选必须已经相对收敛，且层级判断不能太模糊。对 `Market` 这类 node/service/pod 混合的案例，`S2` 往往不应直接开场，而应该放在 `S4` 之后使用。

因此，对 `S2` 的评价是：它确实适合它声称覆盖的资源类案例，但前提是先完成候选压缩和必要的层级消歧。它不是全局第一步，却是资源类 RCA 的关键终判策略。

### S3 传播链回溯验证

`S3` 更像“第二阶段追源策略”，而不是默认起手策略。它在 20 个案例上的平均分为 `1.0`，只有 1 次首选，但有 7 次次选，这说明它经常重要，但通常不是第一步。

从标注看，`S3` 在跨组件传播明显的案例中价值最高，尤其适合两类场景：

- `Market` 中由网络退化或服务依赖导致的上下游传播；
- `Telecom` 中 `docker -> db` 的 JDBC 扇出传播，以及 network / db 类问题的源头回溯。

`S3` 的主要贡献不在于发现“某个局部组件有异常”，而在于判断该组件到底是传播链源头还是下游受害者。因此，它最适合接在 `S1` 后面，用来回答“当前最坏症状点是否只是受害者”这一问题。

因此，对 `S3` 的评价是：它不是广谱策略，但在需要区分传播源与受害者的 RCA 中非常关键。它的定位应是“追源补强”，而不是“通用入口”。

### S4 副本-层级消歧验证

`S4` 是一个强数据集依赖的策略。它在 20 个案例上的整体平均分只有 `0.85`，但这并不表示它弱，而是因为它在 `Bank` 这类纯 pod 层案例里几乎没有发挥空间。

如果只看 `Market`，`S4` 的表现非常强：平均分达到 `2.17`，并获得 3 次首选。尤其是 9、10、11 这组三个 memory 家族案例，分别对应 node、service、pod 三层根因，正好验证了 `S4` 的核心价值，即通过副本分布、共址关系和服务聚合模式，判断“最小解释层级”到底是哪一层。

这说明 `S4` 并不是一个全局都该频繁调用的策略，而是一个在多层部署、多副本结构中不可缺少的专用策略。对于 `Bank`，它大多可以省略；对于 `Market`，它应当前置；对于 `Telecom`，它通常作为网络类和 DB 类之间的辅助消歧手段。

因此，对 `S4` 的评价是：它的普适性不强，但在 `Market` 这类多层级场景中是必要策略。它的价值不在覆盖面，而在解决其他策略难以处理的“层级归因错误”问题。

### S5 语义锚点验证

`S5` 是覆盖最窄、但命中后最强的策略。它在 20 个案例上的整体平均分为 `0.9`，有 5 次首选，同时有 12 个 `0` 分案例，呈现出很明显的“两极分化”。

这种分布其实正符合 `S5` 的设计目标：只有在存在高排他性的日志、JDBC、状态切换或离散事件锚点时，它才应该被优先调用。一旦这些锚点存在，`S5` 的区分力非常强。典型例子包括：

- `Bank` 的 JVM OOM / Full GC；
- `Market` 的 process termination；
- `Telecom` 的 db connection limit / db close。

与 `S2` 不同，`S5` 不是围绕连续资源曲线做解释，而是围绕“如果该类根因真实存在，理应留下什么硬证据”做确认或反证。因此它最适合在发现强语义锚点后抢占执行，而不是排队等待。

因此，对 `S5` 的评价是：它不是通用策略，但在语义型、离散事件型案例中精度最高，适合被设计成抢占式确认模块。没有锚点时不应滥用，有锚点时应优先使用。

## 汇总结论

如果把这 20 个案例压缩成一句判断，那么可以说：

- `S1` 最适合作为默认入口；
- `S2` 和 `S5` 最适合作为终局确认；
- `S3` 最适合作为传播追源补强；
- `S4` 最适合作为多层结构下的层级消歧器。

因此，这组标注结果总体支持当前策略池的设计思路：每个策略都对一类特定问题有明确价值，但它们的价值主要体现在“调用时机正确”时，而不在于谁能单独覆盖全部 RCA 案例。
