## 一、动机:从已经发生的研究里活下来什么

### 1.1 已经走过的三个方向

**Phase 1:反事实验证驱动的 RCA 工作流**(已实现)
- 全模态 + 分类分治 + 反事实二元淘汰
- 在 RE3 上达到 0.967,RE1-TT 上达到 0.448
- **这一层是真创新,论文主线完整且强大**

**Phase 2:情绪向量驱动 agent 行为控制**(在当前数据集不起作用)
- 三个场景、两个数据集、不同准确率水平,情绪向量始终没有产生任何差异
- 物理引擎(全模态 + 分类分治 + 反事实)已经自动做到了"不同案例不同搜索策略"
- **结论范围:在当前 RCA 工作流 + 这个规模 + 单轮离线场景下,情绪向量是多余的抽象层**
- **不等于:在所有 RCA 场景下都没用**

**Phase 4:内驱异质进化 + agent 调参**(在当前数据集不起作用)
- 五代过完,Claude 和 DeepSeek 都收敛到 44.0%(原版 V8.6 的 44.8%)
- 异质 diversity 在搜索路径上验证,但没转化成 performance，纯参数调优空间内，异质搜索的多样性收益被评分函数天花板封印了——要换空间（算子级/资源约束），异质性才能释放价值
- **结论范围:在 V8.6 已接近最优的参数空间内,异质 agent 调参没空间显形**
- **不等于:异质 agent 在所有任务形态下都没用**

### 1.2 三件事各自留下来的真东西

| 来源 | 留下来的 | 可以接续的 |
|------|---------|----------|
| Phase 1 | 反事实验证 + 动态思维链的工程基础设施 | 主线方法 |
| Phase 2 | "状态变量驱动决策"这个想法本身(实现路径要换) | meta-controller 的状态层(可选) |
| Phase 4 | "策略 diversity 在合适场景下可能有用"这个判断 | 策略池(不是调参 agent) |

### 1.3 新方向的核心问题

**当资源受限 + 数据量大时,如何调度反事实验证的搜索过程?**

具体:
- 反事实候选可能有几十上百个
- 每个反事实的验证成本不均匀
- 资源 budget 有限(算力 / 时间 / API call)
- 不同 case 类型适合不同搜索策略
- 需要带状态的渐进式验证,不是全部跑完

**这件事 Phase 1 没做(默认全部反事实做完整验证),Phase 2 想做但场景不对,Phase 4 想做但形态不对**。

## 二、舞台:OpenRCA 作为合适的验证 benchmark

### 2.1 OpenRCA 关键事实

- **来源**:ICLR 2025,Microsoft + 香港中文大学(深圳)+ 清华大学
- **规模**:335 个真实故障 case,68GB 多模态遥测(metrics + logs + traces)
- **来自 3 个企业级生产系统**
- **任务**:LLM 接收 failure case + 自然语言 query,推理出根因组件 + 原因
- **当前 SOTA**:Claude 3.5 Sonnet + RCA-Agent → **11.34% Correct, 17.31% Partial**
- **次优**:GPT-4o + RCA-Agent → 8.96% Correct, 17.91% Partial
- **资源**:论文公开,代码开源(microsoft/OpenRCA),Leaderboard 公开

### 2.2 为什么 OpenRCA 适合验证新方向

**(1) 规模 + 难度匹配**
- RE3、RE1-TT 已接近天花板(0.967、0.448),优化空间小,调度策略差异看不见
- OpenRCA 88.66% 失败空间——任何调度策略的差异都会被放大,容易显形

**(2) 任务形态匹配**
- OpenRCA 任务本质就是"LLM 在大规模异质数据上做多步推理"——这正是"资源调度 + 反事实验证"的天然应用场景
- 不需要重新构造"资源约束"变量——OpenRCA 任务本身就内嵌资源约束(LLM context 长度 + 推理步数限制)

## 三、方法:三层架构

```
┌─────────────────────────────────────────────────┐
│                   输入层                         │
│  failure case + 多模态遥测数据 + 资源 budget    │
└─────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────┐
│              反事实候选生成                       │
│  基于 case 特征,生成可能的根因假设              │
│  (沿用 Phase 1 的反事实生成机制)                │
└─────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────┐
│           Meta-Controller(调度层)              │
│  输入:                                          │
│    - 当前证据池 + 置信度                        │
│    - 资源剩余                                   │
│    - case 特征/类型                             │
│  输出:                                          │
│    - 下一步用哪个策略                           │
│    - 验证深度                                   │
│    - 是否停止                                   │
│                                                  │
│  状态变量(可选):情绪向量或简化状态量          │
└─────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────┐
│              策略池(异质 agent)                │
│  Strategy A: 广撒网浅验证(适合 LOSS+DELAY)    │
│  Strategy B: 深挖单候选(适合 CPU+MEM 突发)   │
│  Strategy C: 因果传播链追踪(适合拓扑型)       │
│  Strategy D: 日志关键词+变更比对(适合配置型)  │
│  ...                                            │
└─────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────┐
│              反事实验证执行                       │
│  执行选中策略,更新证据 + 置信度                  │
│  → 回到 Meta-Controller                         │
└─────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────┐
│                   输出层                         │
│  根因组件 + 根因原因 + 推理链                    │
└─────────────────────────────────────────────────┘
```

### 3.1 反事实候选生成(沿用 Phase 1)

不变化。这一层是 Phase 1 的工程基础设施,已经验证过。

### 3.2 Meta-Controller(新)

**核心职责**:决定"下一步做什么"。

**输入状态——**
- 当前证据池(已验证的反事实集合 + 各自结果)
- 累积置信度(对每个根因假设的当前确信度)
- 资源剩余(剩余算力 / 时间 / API budget)
- case 特征(多模态信号分布、异常时间窗口、涉及组件)

**输出决策——**
- 下一步用哪个策略(从策略池选)
- 验证深度(浅/中/深)
- 是否停止(置信度够 / 资源耗尽 / 边际收益过低)

**实现路径——三种可选方案,优先级递减:**

**方案 A:简化状态量 + 规则化决策**
- 状态量:几个数值变量(置信度方差、资源剩余比、case 复杂度评分)
- 决策:基于规则表(if-then)
- **优点**:可解释、好调试、计算开销低
- **缺点**:规则要手写,泛化性受限

**方案 B:情绪向量作为状态变量**
- 状态量:几个抽象维度(焦虑/确信/不确定/好奇)
- 决策:基于状态向量的策略选择
- **优点**:接续 Phase 2 想法,有理论基础
- **缺点**:需要重新验证情绪向量在这种调度场景下是否真的比简化状态量好——这是 open question

**方案 C:LLM 作为 meta-controller**
- LLM 直接读取当前状态描述,输出下一步决策
- **优点**:灵活,能利用 LLM 的常识推理
- **缺点**:每步调度都消耗 LLM call,资源开销与"资源调度本身的目标"冲突

**初步建议:先做方案 A(规则化基线),再对比方案 B 和 C 是否真的有增益**。

### 3.3 策略池(异质 agent 接到这里)

**和 Phase 4 异质 agent 的区别——**

| 维度 | Phase 4 异质 agent | 新方向策略池 |
|------|------------------|-------------|
| 异质 motivation | 寻找更优参数 | 不同 case 类型分流 |
| diversity 体现 | 参数空间 | 决策序列形状 |
| 评估方式 | 收敛到同一分数 | 各自负责擅长的 case 类型 |
| 验证场景 | 接近最优的参数空间 | 远未饱和的任务空间 |

**策略池的设计原则——**
- 每个策略对应一类 case 的最优搜索方式
- 策略之间互补,不强制收敛
- 策略数量先少再多(初版 3-4 个,验证后扩展)

**初版策略池(基于 OpenRCA case 类型推演)——**

| 策略 | 形态 | 适合 case 类型 |
|------|------|--------------|
| A. 广撒网浅验证 | 多候选反事实并行,每个浅查 | 信号弥散型(LOSS+DELAY) |
| B. 深挖单候选 | 锁定 1-2 候选,深度验证 | 突发型(CPU+MEM) |
| C. 因果传播链追踪 | 沿调用链/依赖图溯源 | 拓扑传播型 |
| D. 日志关键词+变更比对 | 文本匹配 + 时间窗口对齐 | 配置型/部署型 |

**这一层需要在读完 OpenRCA case 类型分布后做精修**——可能合并、拆分、增加。

### 3.4 反事实验证执行(沿用 Phase 1)

不变化。

### 3.5 资源调度的核心机制

**机制 1:budget 感知的策略选择**
- 资源充足 → 偏好深度策略
- 资源紧张 → 偏好浅查/早停

**机制 2:置信度阈值早停**
- 累积置信度超过阈值 → 提前停止
- 阈值可以是固定值,也可以是资源剩余的函数

**机制 3:边际收益评估**
- 当继续验证带来的预期信息增益 < 资源成本 → 停止
- 这一层是最难的,需要对"反事实验证的预期收益"做估计

## 四、效率提升可能性论证

### 4.1 当前 SOTA 的瓶颈分析

**Claude 3.5 Sonnet + RCA-Agent: 11.34% Correct**

**论文中观察到的失败模式(基于摘要推演,需读论文确认)——**
- LLM 在长 context 上 reasoning 衰减
- LLM 在多模态信号融合上挣扎
- LLM 在"应该看哪里"上没有清晰策略
- LLM 在资源/步数限制下容易"放弃" 或"乱猜"

**这些失败模式中,新方向能补的——**

| 失败模式 | 新方向如何补 |
|---------|-------------|
| 长 context reasoning 衰减 | 反事实验证把"全数据 reasoning" 切成"小验证步骤" |
| 多模态信号融合困难 | 策略池中不同策略针对不同模态优化 |
| "应该看哪里"没策略 | meta-controller 显式做"下一步看哪里"的决策 |
| 资源限制下放弃/乱猜 | budget-aware 早停 + 置信度阈值,有原则地停止 |

### 4.2 效率提升预期

**两个维度——**

**(1) 准确率提升(主目标)**
- 假设:策略 diversity 在 OpenRCA 异质 case 上能转化成 performance
- 预期:相比 RCA-Agent 基线,准确率可能有 3-10 个百分点的改进
- **这个数字是推演,不是承诺**

**(2) 资源效率(副目标)**
- 同等准确率下,LLM call 数 / token 消耗下降
- early stopping 机制 + 浅查优先,平均资源消耗可能下降 20-50%
- **这个数字也是推演**

### 4.3 适用性边界

**这个方向适合——**
- 远未饱和的 RCA 任务(SOTA 远低于 100%)
- case 类型异质度高的数据集
- 资源约束有意义的场景(LLM call 成本 / 时间限制)

**这个方向不适合——**
- 已饱和任务(RE3 0.967 这种)
- case 类型单一的场景(策略 diversity 没空间)
- 离线批量 + 资源充足场景(Phase 2 在当前数据集不起作用)

## 五、与现有研究的差异化

### 5.1 vs OpenRCA RCA-Agent

- RCA-Agent 是单策略 LLM-agent,新方向是策略池 + meta-controller
- RCA-Agent 没有显式资源调度,新方向有 budget-aware
- RCA-Agent 不依赖反事实验证,新方向以反事实验证为核心机制

### 5.2 vs Phase 1(自己的工作)

- Phase 1 默认所有反事实都完整验证,新方向加调度层
- Phase 1 单一搜索策略,新方向策略池
- Phase 1 离线批量,新方向支持资源约束下的渐进式

### 5.3 vs 已有 cost-bounded RCA 方法

- 已有方法:静态预算分配 / 固定剪枝规则
- 新方向:动态状态感知调度
- **差异化的关键在 meta-controller 的状态变量层**——这是和已有 cost-bounded 方法的真正区别

## 六、Open Questions

1. **OpenRCA 的 case 类型分布是什么样的?**
   策略池设计依赖于这个,需要读论文 case 分类章节。

2. **方案 A(规则化)、方案 B(情绪向量)、方案 C(LLM as meta-controller)哪个更合适?**
   要做对比实验。

3. **情绪向量在调度层场景下,是不是还会被简化状态量"自动做到"?**
   类似 Phase 2 在物理引擎里被自动做掉的问题。这是核心 risk,需要在小规模实测中验证。

4. **策略池的策略数量边界?**
   太少不够 diversity,太多 meta-controller 选不准。初版 3-4 个,逐步扩展。

### 8.1 已经验证的

- Phase 1 反事实验证 + 动态思维链:0.967 / 0.448
- Phase 2 情绪向量在当前 RCA 工作流上无效:三场景两数据集交叉验证
- Phase 4 异质 agent 在 V8.6 参数空间无效:五代收敛到 44%
- OpenRCA SOTA: Claude 3.5 Sonnet + RCA-Agent 11.34%

### 8.2 推演的(未验证)

- "OpenRCA 远未饱和 → 调度策略差异显形空间大"
- "策略 diversity 在异质 case 类型上能转化成 performance"
- "新方向准确率比 SOTA 高 3-10 个百分点"
- "新方向资源消耗低 20-50%"

### 8.3 未知的

- OpenRCA case 类型具体分布
- 方案 A/B/C meta-controller 哪个更优
- 情绪向量是否会再次被简化状态量自动做掉
- 策略池数量边界

关于meta-controller的方案选择，文档里建议先做方案A（规则化基线），这个判断是对的。但有一个具体的场景可以提前想：当证据池里有两个置信度相近的候选根因时，规则化方案容易卡住（规则表没有覆盖的边界情况）。这个时候方案B（情绪向量）和方案C（LLM）的差异才会显现。所以如果要做对比实验，case筛选标准可以优先选"双候选置信度差 < 0.2"的困难样本，而不是全量测试。
关于OpenRCA子集PoC，文档里提到"选100个case做PoC"，建议再具体一点：按故障类型分层采样，每种类型各20个左右，这样策略池的差异化效果才能在小规模上显形，不然100个case里如果LOSS+DELAY占了80%，策略多样性完全看不出来。
一个文档里没提到的角度：OpenRCA的SOTA是11.34%，这个数字背后有一个值得挖的问题——失败的88.66%是什么分布？如果大部分失败都集中在某一类case，那策略池的价值直接指向那一类；如果失败均匀分布，说明是系统性问题，meta-controller的早停机制反而比策略多样性更关键。这个分析可以完全基于论文，不需要跑数据，适合周四讨论前准备。

### 8.4 风险

**风险 1:Phase 2 教训重演**
情绪向量在新场景下仍可能被简化状态量自动覆盖。
**对策**:先实现规则化 meta-controller(方案 A)作为基线,情绪向量作为可选层。

**风险 2:Phase 4 教训重演**
策略 diversity 在 OpenRCA 上仍可能不转化成 performance。
**对策**:先在 OpenRCA 子集上做 PoC,如果策略池间收敛严重,及时调整。
